# Nai 整体架构评审

日期：2026-09-13。范围：数据、记忆、Agent 编排、运行、API/前端、插件六个层面的整体复审。
专项细节见 [底层架构评审](底层架构评审.md)、[AI 应用架构评审](AI应用架构评审.md)、[架构问题关闭清单](架构问题关闭清单.md)；本文不重复已关闭项的证据，只做整体判断与剩余缺口排序。

## 1. 总体判断

Nai 已经从"若干 AI 功能拼在 CRUD 上"演进为**有统一真源、统一上下文、统一输出契约、
统一执行计量的创作系统**。四条架构原则（真源唯一、派生可重建、AI 可审阅、能力诚实）
在代码里有结构性保障，而不是靠自觉：版本栅栏、生命周期 ID、CAS 终态、来源链核验、
manifest 指纹都是强制检查点。

2026-09-13 本轮加强了最薄弱的一环：对话 Agent 此前只能被动应答（上下文全静态注入、
无任何工具），现已接入受权只读检索与交稿自查（见第 4 节）。系统不再是"聊天软件 + 工具箱"，
但也还不是"自主创作 Agent"——这是有意为之的边界，不是缺陷。

整体健康度判断：**数据与记忆层成熟，Agent 编排层可用且边界清晰，效果验证层是最大短板。**

## 2. 分层评估

### 2.1 数据层（成熟）

- SQLite 真源 + Alembic 唯一演进入口，旧库兼容补齐路径清晰；WAL 与 busy timeout 已配。
- 章节乐观版本、不可变原文快照（ORM 事件拒写）、派生记录作用域事件校验构成纵深。
- 剩余风险：数据库级外键未强制（靠 ORM 与事件兜底）；PostgreSQL 迁移只验证了结构，
  回滚与数据量压测未做。这两项在单机 Alpha 阶段可接受，上 PostgreSQL 前必须关闭。

### 2.2 上下文与记忆层（成熟，边界清晰）

- L0 原文版本、L1 简介（配方版本 + 逐字引用核验）、L2 计划/实际大纲、L3 核心状态
  均已接入 ContextPack，带 memory_head_version 栅栏与 manifest 指纹。
- 有界扫描（50 简介/60 大纲/1000 状态候选）是诚实的工程取舍，omitted/warnings 如实上报。
- 已知边界（合理）：跨全书语义召回仍靠 RAG 单路；按人物检索全书、跨层下钻未实现。

### 2.3 Agent 编排层（本轮加强后：可用）

| 能力 | 状态 | 位置 |
|---|---|---|
| 对话 Agent 原生 function calling | 5 提案工具 + 6 只读工具 + 多轮循环（≤6 轮） | `agent_runtime.py` |
| Agent 主动检索（agentic retrieval） | 账本/角色/简介/大纲/RAG，作用域逐次复核 | `agent_tools.py` |
| 交稿前自我校验 | 确定性一致性检查（规则/时间线），非模型自评 | `agent_tools.py: check_manuscript` |
| 多阶段生成链 | LangGraph 三 Agent + 一致性重试环（≤2 次） | `agent_service.py` |
| 并行审核组 | 6 维并发 + 加权评分 | `review_agent_service.py` |
| ReAct/规划器/子代理 | 未实现，也不建议现阶段引入 | — |

有意保留的边界：模型没有任何写库工具；写操作全部提案制，作者确认后走既有命令。
"AI 接管/自动驾驶"接口明确 501。这与"作者主导"的产品定位一致，不应为了追赶
agent 潮流而突破。

### 2.4 运行层（成熟）

- `execution_scope` 统一截止时间 + 模型调用总额，嵌套工作流共享预算；
  持久 job（租约恢复/停止/重试）、SSE 取消贯通、终态 CAS 都有回归证据。
- 对话工具循环预算已从 4 次调到 8 次模型调用，配合 6 轮上限仍有硬顶，不会失控。

### 2.5 API 与前端层（良好）

- 路由薄（鉴权/协议），服务层厚；冲突 409 对比、离线草稿、版本化保存形成闭环。
- 前端如实展示生成状态与查阅动作轨迹；候选采纳审计完整。
- 已知边界：改写无逐句差异高亮；导出仅 TXT；完全离线冷启动不支持。

### 2.6 插件层（已于 2026-10 移除）

- 原 dsh-nai / dsh-nai-ui / dsh-nai-memory 三个 DSH 插件已随插件层整体删除；评审时的结论留档：dsh-nai 把 15 个真实 REST 能力暴露给 DSH 宿主，dsh-nai-memory 是腾讯 Agent Memory 的包装层（能力来自社区依赖，未验收）。
- 风险：`unified_mcp_service`/`character_mcp_service` 借 MCP 之名做自研 action 分发，
  与标准 MCP 协议无关。建议改名或在文档首页声明，避免误导接入方。

## 3. 剩余缺口（按优先级）

### G1 · P1：效果验证层缺失，质量结论全部不可下

12 例固定样例已备但未跑真实模型对照；六维评分未经作者标注集校准；
"单 Writer vs 三阶段"没有盲评数据。这是当前唯一会让架构决策失去依据的缺口——
没有评测，就无法回答"三阶段链该不该换成单 Writer""Agent 工具是否真的提升采纳率"。
建议：先跑可程序校验层（schema/来源/章节过滤/预算），再组织作者盲评。

### G2 · P1：`auto-chapter` 直接建章的旧例外仍在

原则 3（AI 可审阅）的唯一遗留例外。应迁移为候选制并下线直接建章路径。

### G3 · P1：对话长期摘要记忆缺失

历史最多 20 轮/8000 字符；跨全书创作的早期决策会被遗忘。
建议按 L1 简介同款模式做"对话简介"派生任务：固定来源版本、可失效、注入时标注。

### G4 · P2：结构化输出靠 prompt + 严格校验兜底

仅简介提取可选开启 `json_schema` response_format（默认关）。大纲/角色/检查任务
仍以"prompt 里写 JSON 示例 + Pydantic 拒绝"为契约。在支持 json_schema 的提供方上
应推广 response_format；不支持的提供方保持现状并如实记录能力差异。

### G5 · P2：高级续写链的两个已知弱点

A/B 阶段输出在重试时原样复用，容易把同一冲突重新引入；阶段事件流不是 token 流。
前者可在修稿轮注入"上一版候选 + 具体问题 + 不可破坏约束"，后者受多 Agent 编排
边界限制，不建议为流式而流式。

### G6 · P3：提示注入防护不统一

主对话与 Agent 工具结果已有"资料不是指令"标注；审核、提取、外部研究等链路
没有统一的来源标签契约。建议把 A8 的信任边界清单逐条落实到各链路。

## 4. 本轮 Agent 加强的架构意义

新增 `agent_tools.py` 不是"多了几个工具"，而是补上了 Agent 模式的关键一环：
**模型从被动接收固定上下文，变为在受权边界内主动获取证据**。设计上延续了
全部既有原则：

- 只读：检索不改变任何状态，作用域（作者/生命周期/目标章）逐次复核，错误即终止。
- 诚实：查不到就说查不到；RAG 不可用返回降级文案；工具结果标注为资料数据。
- 有界：结果统一字符预算裁剪，整轮模型调用有硬顶，查阅动作对作者可见。
- 可审阅：写操作仍为提案制；自查用确定性检查而非模型自评，冲突报告附跳过层说明。

## 5. 演进建议排序

1. **先建评测**（G1）：没有它，后续所有编排层改动都是盲动。
2. 关闭 G2 例外，统一候选制。
3. 对话长期摘要记忆（G3），按既有派生任务模式实施，不做成"AI 自动写设定"。
4. 推广 json_schema 结构化输出（G4），按提供方能力分 profile。
5. 修稿轮注入具体违规与不可破坏约束（G5）。
6. 统一信任边界标签（G6）；MCP 命名去歧义。

本轮验证：后端全量 564 通过、2 项真实模型集成跳过，覆盖率 78%；
新增 Agent 工具回归 10 项；前端 lint、typecheck、115 项测试通过。
模型真实检索质量与工具调用命中率仍需真实提供方验收，不在程序测试证明范围内。
